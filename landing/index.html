Платёж принят за миллисекунды. Всё остальное — асинхронно, а итог приходит webhook-ом.

Микросервисный процессинг: API отвечает 202 Accepted, событие уходит через outbox в RabbitMQ, stateless-процессор идёт в эмулятор платёжного шлюза, владелец данных фиксирует результат и уведомляет клиента. С ретраями, DLQ и трассировкой каждого платежа.

01 / запуск

Три команды — и стенд жив

Значения по умолчанию рабочие, .env можно не трогать. Через 2–5 секунд после POST платёж перейдёт в succeeded или failed, а webhook уйдёт получателю.

~/payments-processing — zsh 
# поднять стенд
$ docker compose up -d --build

# создать платёж
$ curl -X POST localhost:8000/api/v1/payments \
    -H "X-API-Key: secret-api-key" \
    -H "Idempotency-Key: order-1042" \
    -H "Content-Type: application/json" \
    -d '{"amount":"1500.00","currency":"RUB",
         "description":"Заказ #1042",
         "webhook_url":"http://webhook-receiver:8080/anything/shop"}'
→ 202 {"payment_id":"…","status":"pending"}

# через 2–5 секунд
$ curl localhost:8000/api/v1/payments/<id> \n    -H "X-API-Key: secret-api-key"
→ "status":"succeeded", "webhook_delivered_at":"…"

04 / решения

Что может пойти не так — и что с этим сделано

Платёж записан, а событие потерялось при падении?

Outbox. Платёж и событие пишутся одной транзакцией, relay публикует с publisher confirms. Гарантия at-least-once.

Клиент повторил POST — будет второй платёж?

Идемпотентный API. UNIQUE-ключ и ON CONFLICT DO NOTHING. SHA-256 тела отличает повтор (202, тот же id) от конфликта (409).

Сообщение доставлено дважды — двойное списание?

Идемпотентный шлюз. Idempotency-Key = payment_id: повтор возвращает сохранённый результат. Статус меняется только из pending.

Шлюз тормозит — страдает база?

Stateless-процессор. Соединений с БД нет, данными владеет только payments-service. Процессор масштабируется отдельно.

Сбой временный или постоянный?

Ретраи и DLQ. 5xx, таймаут, 429 — retry-очереди с TTL 1 с и 2 с. Битое тело и 4xx — сразу DLQ. Своя очередь на каждую задержку, без head-of-line blocking.

Где застрял конкретный платёж?

Трассировка. OpenTelemetry → Jaeger, поиск по payment.id. Упавшие попытки красные, уход в DLQ — в атрибуте спана.

05 / жизненный цикл

Один переход — из pending

failed от шлюза — бизнес-результат, а не ошибка: он фиксируется и сообщается клиенту, ретраи на него не тратятся.

  1. POST → 202

    Платёж pending, событие лежит в outbox

  2. pending

    Процессор ждёт ответа шлюза 2–5 с

  3. succeeded · failed

    Единственный переход статуса, первый результат побеждает

  4. webhook

    5xx, 408, 429 — ретраи; прочие 4xx — сразу DLQ

  5. доставлен

    webhook_delivered_at = now()
